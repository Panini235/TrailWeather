## 3. 已确认的问题

### P0：天气与离线正确性

**A-01 跨小时后无法复用已经存有后续时次的预报。**

`lib/ui/map/point_weather_sheet.dart:16` 每次查询使用“当前整点至后 24 小时”；`lib/data/weather/weather_repository.dart:185` 将完整起止小时放入缓存键，按精确键查找。10:00 查过一次，即使响应已含 48 小时数据，11:00 请求仍换键；此时断网会失败。诊断探针以包含 48 小时数据的假来源复现。线路改变出发时间、节点集合或坐标同样可能失配。

整改：将预报持久化为“来源、查询点、模式/参数版本、预报批次、实际覆盖区间”的快照；查询时选取覆盖目标时次的数据。离线包索引与临时缓存独立，固定用户下载的行程包，不被普通 LRU 淘汰。

**A-02 很旧的缓存不刷新；较新的旧缓存刷新失败会产生未处理异步错误。**

`weather_repository.dart:111–141` 对任何可解码缓存都直接返回；仅当过期且存储时间距今不足 6 小时时后台刷新。7 小时以上的缓存会带 stale 标记返回，但不再尝试联网。`unawaited(_fetchAndStore(...))` 没有失败处理，断网刷新异常会逃出仓库。`getRouteWeatherBundle` 也未向 UI 传递后台完成通知，后台成功不保证当前界面更新；旧数据提示却写“正在后台刷新”。

整改：把新鲜/过期/离线快照分开；在线始终可发起刷新；失败保留有明确时效的旧数据并显示刷新失败；捕获异步异常，成功后通知 UI；增加“最后成功更新/覆盖至/数据已旧多久”。

**A-03 节点查询身份没有包含坐标和方向。**

`lib/ui/detail/route_detail_screen.dart:34–64` 的 `DetailFetchKey` 只用 query 加节点数、首尾累计距离比较；`HikingRoute.reversed()` 保留 route ID。节点数与总距离相同时，正向和反向的 key 相等，即使首节点位置已经互换，可复用原方向 bundle 的按序映射。标记/修改路线后节点数不变也有同类风险。探针明确复现 key 碰撞。

本次浏览器所选香山示例在反向后节点数从 7 变为 8，触发了新请求；因此本条不能描述为“所有路线反向都会出错”。

整改：查询身份纳入稳定的节点坐标/顺序/路线版本及相关天气参数；测试相同节点数和总长度的正反向路线，断言每个节点绑定的请求坐标正确。

**A-04 “当前位置天气”的时间锚点停留在上次定位。**

`lib/ui/map/map_home_screen.dart:350` 保存 `_myFixAtUtc`，`_openMyLocationWeather` 在 436 行附近继续传该时间；点位面板请求与选时也使用这个固定值。代码没有页面恢复或定时刷新机制。停留数小时后再次打开，查询的可能仍是旧时间点。定位时间与天气有效时间应分别展示。

整改：打开当前天气时重新取当前时间，按时效和前后台状态刷新；保留定位时间与位置精度；允许用户手动刷新；离线显示“某时下载的预报”，不标成刚更新。

### P0/P1：徒步目标尚未覆盖

**A-05 离线包只有入口和说明。**

`route_detail_screen.dart:374` 的按钮只打开“开发中”对话框。没有下载任务、文件清单、校验、容量管理、离线覆盖图、重试/续传、断网冷启动契约。`CacheStore` 的地图命名空间不等于实现了离线地图。当前底图是在线瓦片。

**A-06 山地和多日场景仍不完整。**

`WeatherRepository.approxGridDeg=0.1` 的近似合并会让相邻节点共用查询结果；没有按节点海拔请求或地形细分。T-125 仍待办。出发窗口 T-130 未实现；营地标记和停留时间已有，但多日按营地/行走时段拆分与逐日预警未完成。现有设置中的海拔修正字段也不代表修正引擎已实现。不要以固定气温递减率承诺“真实山顶微气候”。

**A-07 徒步中模式及运营保障不足。**

当前以单次前台定位、行前 ETA 为主。尚无完整“正在徒步”状态管理、随进度更新的预计到达时刻、位置新鲜度统一展示、弱网重连流程与真实续航证据。连续后台轨迹记录不是本次天气目标的必需前置；应先完成低耗电前台定位和无网查看闭环。

**A-08 国内天气与商业数据路径未闭环。**

默认来源是 Open-Meteo 两个模型和 MET Norway；和风需每位用户自行输入 Host/Key。代码中和风格点适配器仅支持 `/v7/grid-weather/24h`，其现有接入无法覆盖“下周徒步”。正式消费产品应通过自己的天气网关使用授权数据，集中做密钥管理、限流、可用性监控和明确标注的来源降级。商业 Open-Meteo 当前仍被硬编码为免费主机，购买授权后还需要接入 customer 主机/认证。[S5]

### P1：UI 与表达

**A-09 首页和详情页的信息顺序不符合快速查天气。**

首页只显示线路事实，没有当前位置天气、已计划的出发时间、最近更新、风险摘要与离线准备状态。390×844 下，详情首屏基本由地图、线路事实和选择器占满，天气摘要需要继续向下找。建议首页增加“当前位置/常用地点天气”和“即将出发”；行程卡显示出发时间、主要天气风险、预报更新时间、离线状态。详情顶部先展示所选日期/时间的天气摘要，地图可折叠。

**A-10 暗色模式存在明显可读性问题。**

实测来源选择器文字接近黑色；Pro 页面多个正文使用固定 `Colors.grey.shade700`，而支付未接入提示使用很浅的橙色背景、继承浅色正文，导致提示难读。截图：`detail-dark.png`、`paywall-dark.png`、`onboarding-dark.png`。应用主题色的成对前景/背景，覆盖 360–430px 宽度、浅深色、大字体和户外亮度测试。

**A-11 产品文案仍超出实现。**

引导页仍有“未来 7 天微气候窗口”“绝不崩溃”；付费墙权益描述仍有“精准推演…真实体感与冰点”。即使标记开发中，也应改为已实现能力或明确的估算/规划。全局 7 天承诺与不同来源真实覆盖也不一致。

### P1：收费与发布

**A-12 订阅服务没有真实后端闭环。**

`Billing.available=false`，购买被阻止；`subscription_repository.dart:41–86` 的禁用分支之后仍是本地写权益和本地恢复逻辑。把开关改成 true 会重新走本地授予 Pro 的路径，不能作为接入支付的方法。没有商店 SDK、服务端验单、订阅事件、用户绑定、退款撤权或跨设备恢复。价格/试用天数是静态展示，正式销售应取渠道商品信息和资格。

当前测试验证了“禁用时不授予 Pro”，没有证明真实订单、续费或退款链路正确。应替换本地模拟路径，不能在其上简单打开按钮。

## 4. 无网络时应达到的验收标准

无网时能查看的是**离线保存的预报**；预报有有效时间和不确定性。新增天气、远端更新的官方预警仍需要通信能力。产品应清楚区分定位可用、地图可用、预报缓存可用和网络可用四种状态。

建议第一版的交付分两层：

1. **基础行程包**：原始/分析轨迹、航点、路线版本、出发时间、行进方向、配速、逐节点完整可用时段预报、来源/获取时间/预报批次/有效覆盖、已获取的预警及其失效时间。日期范围由真实来源覆盖决定，不能保证每个来源都有 7 天。
2. **授权地图包**：沿线路走廊下载指定缩放级别或授权矢量数据；出发前展示范围、大小、缺失区块、完整性校验。底图许可解决前，基础包仍应可看轨迹/航点/坐标，明确提示底图不可用。OSM 公共标准瓦片明确禁止用于离线预下载，应采用有相应权利的服务或自托管数据。[S4]

验收场景：

- 有网下载后，开启飞行模式，彻底退出 App，再冷启动；能够打开行程、轨迹和覆盖时段内的天气。
- 跨小时、跨午夜、切换预报日期与节点后仍能查到包内已有数据；包外时段明确提示未下载/来源无数据。
- 断网 24/48/72 小时后依然可以读取，醒目标出下载时间、预报有效时间和旧数据状态；不把旧预警标成正在生效，也不把无新预警当作无风险。
- 下载部分失败、空间不足、文件损坏、来源缺字段时不显示“准备完成”。普通缓存清理不得误删已固定行程包；单独提供包删除操作。
- 在线更新失败不损坏已完成的旧包；恢复网络后原子替换为校验完成的新包。
- 已下载的行程资料在途中不因会员到期立即锁死或删除；新下载/更新权益由产品规则控制，数据新鲜度必须一直可见。
- Android/iPhone 真机验证前台 GPS 无网定位、位置误差、无新定位回退、低电量、亮屏耗电和重启。

## 5. 订阅产品建议

建议先以**月度、年度两档**建立真实可交付权益；将终身套餐后置。天气、瓦片和后端会持续产生成本，当前 `¥198` 买断“全部未来在线服务”的承诺没有成本测算支撑。现在的 `¥18/月`、`¥98/年`、`¥198 终身` 均应视为方案占位，不是已售商品或已验证价格。

- 免费：当前位置与基础未来天气、基础轨迹导入、数据更新时间/缺失提示、已下载资料读取、基础阈值提示。不要把说明数据已失效或已下载文件的读取藏在付费墙后。
- Pro 候选：更多行程离线包、已授权的地形地图、不同出发时刻比较、长线/多日计划、扩展来源对比。仅对已完成并验证的权益收费。
- 官方预警应清楚标示来源和时效；联网推送可作为后续服务，但离线时不能承诺收到新预警。
- 试用是否存在、可用天数和资格由商店/商户配置和返回结果决定，不应写死每个用户都有 7 天。
- 定价需根据每次路线采样点数、模型/时段使用、天气授权计费口径、地图下载量、后端成本、渠道费用、退款与客服成本测算。

所有 Secret、商户私钥、API v3 key、Apple `.p8`、服务账号私钥等应由用户/管理员放入部署环境密钥管理器或 CI Secrets；项目只提交配置名称和读取方式。无需在聊天中发送私钥。

除支付资料，还需天气服务的商用套餐/接口范围（至少覆盖目标预报窗口）、离线底图许可及 Key、后端域名/部署环境、隐私政策/服务条款主体和客服渠道。天地图或其他底图的在线 Key 本身不能作为离线再分发授权证明。

## 7. 完整订阅系统的实现边界

以下接口为**拟议的项目后端契约**，当前仓库均未实现：

- `GET /v1/billing/catalog`：渠道、商品映射、权益说明；商店端购买价格以商店返回为准。
- `POST /v1/billing/orders`：国内收款通道服务端建单，返回客户端拉起支付所需参数。
- `POST /v1/billing/verify`：接收 Apple 交易或 Google purchase token，服务端向对应平台校验并绑定用户；客户端“成功”回调不直接授予权益。
- `POST /v1/webhooks/{provider}`：签名校验、事件持久化、幂等、乱序处理、重试；必要时回查渠道最终状态。
- `GET /v1/me/entitlements`：服务端计算的权益、到期时间、最新校验时间、渠道及管理订阅入口。
- `POST /v1/billing/restore`：重新向渠道查询并合并合法购买，处理换机和重装。
- `GET /v1/me/offline-license`：签名离线权益凭证；离线读取政策与下载政策分开。

后台需要用户标识、商品映射、订单/交易流水、订阅状态、渠道事件、权益、审计记录与对账任务。最低覆盖：待支付、有效、试用、已取消但仍有效、续费失败/宽限、过期、退款/撤销。Google 和 Apple 的服务端通知与平台查询接口用于跟踪续费、到期和退款状态，业务层必须处理重复和延迟通知。[S6][S7]

离线权益不能只信 SharedPreferences 的 Pro 布尔值或设备时钟。建议使用服务端签名、明确失效时间及产品宽限规则的凭证；服务端保存上次合法状态，回网后校验。设备时钟回拨和多设备滥用须有验证策略，同时避免把已下载的野外资料突然锁住。

完成标准：沙盒真实下单 → 权益生效 → 重复通知不重复授予 → 取消后到期前仍有效 → 续费失败按规则宽限 → 退款/撤销回收权益 → 重装/换机恢复 → 离线读取 → 回网同步。通过后才进入真实金额小额验收和正式发布；账号开通、收费/付费基础设施与商店发布由用户授权执行。
